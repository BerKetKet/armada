# Brief 0.3.1 — Daemon shutdown, protocol docs, known limits, report audit

> Note: this brief was authored before 0.3.2–0.3.4 but is issued after them.
> Numbering is kept for record continuity. Work against current master
> (4317f51 or later), not the state when it was drafted.

## Context

Armada's root daemon (app_process + su, module :daemon) is alive and
device-verified. Remaining Phase 0 housekeeping: the daemon has no defined
shutdown story, the wire protocol exists only in code and test names, the
daemon's operational limits are undocumented, and older reports may describe
pre-0.3.3 behavior that no longer matches source.

No new dependencies. No redesign. Minimal, focused changes.

## Task A — Graceful daemon shutdown

Trigger: SIGTERM (this is how the daemon is actually managed — pkill was used
during the 0.3.4 test).

On SIGTERM the daemon must, in this order:
1. Stop accepting new connections (close the listening socket).
2. Cancel or complete in-flight request handling within a bounded timeout
   (5 seconds is fine; make it a named constant).
3. Shut down all executors without leaking threads.
4. Delete the pid file (daemon.pid) if the daemon created it.
5. Append a shutdown record to the daemon log.
6. Exit with status 0.

Verification is by reading state back, not exit codes alone:
- pid file absent after shutdown
- process gone (ps)
- socket no longer listening
- shutdown record present in daemon.log

Add unit tests for whatever shutdown logic is testable in isolation (executor
termination helper, timeout constant behavior). Do not fake coverage; state
in the report what could not be unit tested and why.

## Task B — Protocol documentation

Create docs/protocol.md documenting:
- Transport: socket path and type
- Framing: line-delimited JSON, in-house codec
- Handshake: hello exchange for root peers; for non-root peers the daemon
  sends ONLY the denied error (post-0.3.3 behavior) and closes
- Frame shapes: version field, hello, echo, error taxonomy including the
  denied error
- Current CLI operations (hello, echo, and anything else that exists)

Derive every shape and path from the current source — do not copy examples
from this brief or from older reports. If source and any older doc disagree,
source wins and the disagreement gets noted in your report.

## Task C — Daemon known limits

Extend docs/daemon.md with a "Known limits" section covering at minimum:
- No persistence across reboot; no auto-restart on crash
- Single daemon instance assumed; pid file semantics
- Log and pid file locations
- Client authentication is limited to the root UID check — any root process
  on the device can connect
- Anything else you observe in source that a user would reasonably need to
  know before relying on the daemon

## Task D — Report accuracy audit

Cross-check the factual claims in docs/reports/0.3-daemon.md and
docs/reports/0.3.3-handshake-race.md against current source. Where a report
describes behavior that 0.3.3 changed (notably the hello-then-denied
sequence), correct it. List every correction in your report with before and
after text. Do not touch reports for style — only factual mismatches with
current source.

## Commit and push discipline

One logical change per commit, in this order:
1. Shutdown implementation + tests
2. docs/protocol.md
3. docs/daemon.md known limits
4. Report corrections

Push each commit separately and wait for CI green before the next. Include
this brief file as docs/briefs/0.3.1-shutdown-docs.md in the first commit.
Write docs/reports/0.3.1-shutdown-docs.md at the end, committed last, with
the full commit list, test output copied from captured runs, the device
verification steps for Task A and their results, and an honest deviations
section (batch pushes, failed attempts, tests not run, anything cached).

## Device verification for Task A

After the code lands: start a fresh daemon on the Pixel 2 XL, confirm a root
CLI hello works, send SIGTERM, then verify the read-back state above.
Gash will handle anything requiring interaction beyond adb.
